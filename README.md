# d1 X checker

X (Twitter) の**フォロー中**一覧で「こちらからはフォローしているが、相手からはフォローされていない相手」だけを見つけ、
その垢の名前・bio・フォロー数・フォロワー数をローカル LLM (LiquidAI d1) に渡し、
**ユーザーが設定した条件に当てはまるかを判定させて、当てはまった行をハイライトする** Brave/Chrome 拡張。

外部サービスには何も送らない (判定は 127.0.0.1 の llama.cpp サーバ)。

## 現状 (2026-10-16)

* 動いている: 一方的フォローの検出、条件の送信、判定、ハイライト、キャッシュ、SPA 追随、判定ログの書き出し。
* **未確定: 実 X での bio / フォロワー数の抽出。** 実 DOM の bio 要素と、一覧 GraphQL 応答に
  `followers_count` が含まれるかを実機で確認中。取れない行は `自己紹介: (なし)` として判定され、
  パネルと popup に「入力不足 N 件」が出る。詳細は下の「実データで見つかった不具合」を参照。
* 精度は入力に強く依存する。bio が空のまま判定した結果は名前からの推測で、体感 2 割は外す。

```
x.com/<自分>/following
  ├ DOM: UserCell を読み、名前 / @handle / bio / 「Follows you」の有無 を取る
  ├ MAIN world: X 自身の GraphQL 応答を傍受し、followers_count / friends_count / followed_by を拾う
  ↓
service worker: 条件を noul 質問に変換 → POST http://127.0.0.1:8081/v1/systemone
  ↓
確率 >= 閾値 の条件があれば、その行をハイライト + 「条件一致 87%」バッジ (ホバーで条件ごとの確率)
```

## セットアップ

### 1. 判定サーバ (d1) を起動

```bash
scripts/d1-server.sh start        # d1-3B  :8081 (既定)
scripts/d1-server.sh start 600m   # d1-omni-600M :8082
scripts/d1-server.sh status
scripts/d1-server.sh probe        # 1 件だけ投げて動作確認
scripts/d1-server.sh stop
```

dGPU は cardwire 経由で使う (`cardwire launch --gpu 1 ...`)。スクリプトがその形で起動する。
モデルやパスは環境変数で上書きできる (`D1_MODEL_PATH`, D1_PORT, D1_LLAMA_DIR)。

### 2. 拡張を読み込む

1. Brave で `brave://extensions` を開く (Chrome なら `chrome://extensions`)
2. 右上の「デベロッパーモード」を ON
3. 「パッケージ化されていない拡張機能を読み込む」→ このディレクトリ (`~/dev/OWN/d1-x-checker`) を選ぶ

### 3. 使う

`https://x.com/<自分>/following` を開く。右下にパネルが出て、対象件数 / 判定済み / 一致件数が進む。
条件一致した行は枠が光り、右上に確率バッジが付く。ツールチップで条件ごとの確率が読める (閾値の調整に使う)。

条件の編集は拡張の「設定」(オプション画面)。1 行 = モデルへの yes/no 質問 1 つで、日本語でそのまま書ける。

## 実測 (このマシン、RTX 5060 / CUDA)

判定 1 件あたり **約 70ms** (3B, 条件 2 件)。キャッシュ済みの行は再判定しない。

### モデルの比較 (同じ質問・同じ入力)

| アカウント | 特徴 | d1-3B (Q4_K_M) | d1-omni-600M (Q8_0) |
|---|---|---|---|
| フォロバ勧誘 (`相互フォロー歓迎！フォロバします！` / 4820 following, 312 followers) | 検出したい | フォロバ要求 **0.91** | 0.91 (ただし他も 0.6-0.7 で分離せず) |
| 企業公式垢 (12 following, 45120 followers) | 検出したい | スパム **0.87** | 0.79 (実在個人も 0.62 で分離せず) |
| 個人エンジニア (187/203) | 除外したい | 両方 **0.02-0.06** | スパム 0.62 = 誤爆 |
| 個人 (95/88) | 除外したい | 両方 **0.04-0.11** | フォロバ 0.78 = 誤爆 |

**結論: 判定には d1-3B を使う。** 600M は質問への回答が 0.5〜0.9 に張り付いて分離せず、
「実在の個人」を条件一致と誤判定する。同じ拡張のまま設定のエンドポイントを `:8082` に変えれば 600M も試せる。

## 実データで見つかった不具合 (2026-10-16, 修正済み)

実機 (Brave, X のフォロー中 268 件) の判定ログを読んだところ、**モデル以前に入力が壊れていた**。

| 症状 | 原因 | 修正 |
|---|---|---|
| bio が全件 `(なし)` → 名前だけで判定 (企業垢が 0.5〜0.96 で乱れていた) | GraphQL の URL 判定が `/i/api/graphql/` 限定で、`api.x.com/graphql/` 等を取り逃していた。さらに `core`/`legacy` に分かれた User object を拾えていなかった | URL 判定を `/graphql/` に拡大。`core`+`legacy`+`relationship_perspectives` を 1 件にまとめる実装に変更 (legacy に screen_name が無くても OK) |
| 「フォロー数: 41650079726」等の異常値 | 一覧 DOM のテキストから数値を拾おうとして、**handle の数字 + 「フォロー中」ボタン**を誤マッチ | DOM からの数値取得を廃止。数値は GraphQL からのみ |
| bio が testid 無しの div にある場合に取れない | `data-testid="UserDescription"` 決め打ち | testid が無ければ「名前ブロックでもボタンでもない最初のテキスト」を bio とみなす |
| プロフィールから「フォロー中」へ SPA 遷移すると動かない | 読み込み時の URL でしか判定していなかった | pushState/replaceState を監視し、URL が変わった時点で開始/後片付け |
| 精度が悪い原因が分からない | どの入力で何を返したかが残っていない | 判定ごとに state・条件・確率を保存し、設定画面の**「判定ログを保存」**で JSON に書き出せるようにした |

### 2 回目 (同じ実機 96 件を再判定)

| 症状 | 原因 | 対応 |
|---|---|---|
| bio が**表示名のコピー**になっていた (`自己紹介: Tesla` / `もの` / `PI` 等、全 96 件) | 実 DOM では bio の要素に `UserDescription` が無く、フォールバックが**名前の div を拾っていた** | 表示名・handle と同じ文字列は bio として採用しない (正規化して比較)。取り違えたまま判定しない |
| 数値がまだ 0 件 | 一覧の GraphQL 応答に `followers_count` が無い可能性が高い (bio の `description` も payload 次第) | 実物を確認するため popup に**「DOM/応答を保存」**を追加 (直近の GraphQL 応答 + 1 行目の HTML + 解析結果を JSON で書き出す) |
| 分離が悪い (Tim Cook 0.71 = 誤爆 / 虚構新聞 0.34 = 取り逃し) | 入力が名前だけなので、モデルは名前から推測しているだけ | 入力が直るまでは条件の調整に意味がない。まず「入力不足」件数を 0 にする |

**入力が空のまま判定した行は、右下パネルと popup に `bio/数値が取れない行あり (N)` として出る。** これが 0 でない限り、判定精度の話をしても意味がない。

修正後 (フィクスチャでの通し確認): 5 件の一方的フォローを判定し、企業垢・勧誘垢が bio と数値付きで正しく一致。
handle が数字入り (`Taro12345678`) でもボタンの数字を拾わず、名前だけの div は bio として採用しない (`momo_lab` は
`自己紹介: (なし)` になり、パネルに「入力不足 1」が出る)。

## 判定ログを見る

設定画面 →「判定ログを保存」で `~/Downloads/d1x-log-*.json` が出る。中身は
`{ settings, conditionsMeta: {署名: {条件と閾値}}, verdicts: [{handle, state, answers, matched, counts}] }`。
`state` がモデルに渡した入力そのままなので、**bio や数値が空なら抽出が壊れている**とすぐ分かる
(ページ右下パネルと popup にも「入力不足 N 件」として出る)。

## 条件文の書き方 (実測に基づく)

同じ垢でも質問文で結果が変わる。**漠然とした意図**より **bio に現れる事実**を聞く (3B, 勧誘垢 1 件と個人垢 2 件):

| 質問文 | 勧誘垢 | 個人垢 |
|---|---|---|
| 「フォロバ目的で大量にフォローしているアカウントか」(意図を推測させる) | 0.19 ✗ | 0.11 / 0.06 |
| 「プロフィールでフォロバ(相互フォロー)やいいね周りを求めているか」(bio の事実) | **0.91** ✓ | 0.06 / 0.05 |

企業垢の検出 (企業垢 2 件 / 個人垢 2 件 / 官公庁垢 1 件):

| 条件 | 企業垢 | 個人垢 |
|---|---|---|
| 「企業・店舗・団体の公式アカウントか」(日本語・1 論点) | 0.97 / 0.97 | 0.10 / 0.16 |
| `It is a corporate account (e.g., followers > 10x following, ...)` (英語・複合) | 0.83 / 0.91 | 0.04 / 0.05 |
| 「フォロワー数がフォロー数の10倍以上か」(数値比較をモデルにやらせる) | 0.58 / 0.72 | 0.10 / 0.13 |

* 日本語で 1 論点ずつ聞くのが最も分離する。
* **数値の比較をモデルに期待しない** (計算機ではない)。数値条件は bio 条件と分けて書くか、JS 側で判定する。
* 閾値 0.4 は緩い。企業垢の除外なら 0.6〜0.7 で足りる。誤爆が嫌なら上げる、漏れが嫌なら下げる。

## 構成

| ファイル | 役割 |
|---|---|
| `src/inject.js` (MAIN world) | X の fetch/XHR を読むだけ (`/graphql/` なら拾う)。pushState を監視。追加リクエストは出さない |
| `src/scan-users.js` (MAIN world) | GraphQL 応答から bio/カウント/followed_by を拾う。フラット形と core/legacy 形の両対応 (テスト対象) |
| `src/parse-cell.js` | UserCell 1 個の解析 (handle / name / bio / Follows you)。数値は取らない |
| `src/content.js` | SPA 追随、走査、判定依頼、ハイライト、右下パネル |
| `src/background.js` | 判定キュー、キャッシュ (chrome.storage)、条件メタの保存、badge 表示 |
| `src/common.js` | state 組み立て、条件→質問変換、閾値判定、キャッシュキー (テスト対象) |
| `src/options.*` | 条件エディタ (名前 / 質問 / 閾値 / 有効)、接続確認、**判定ログの書き出し** |
| `src/popup.*` | サーバ状態、このタブの集計 (入力不足の警告つき)、再判定、キャッシュ削除 |

## 制約

* X 側の DOM と GraphQL の形に依存している。変わったら `parse-cell.js` と `scan-users.js` を直す。
  「Follows you」は `data-testid="userFollowIndicator"`、無ければテキスト (`Follows you` / `フォローされています`) で判定。
  一方的フォローは GraphQL の `followed_by` を優先し、無ければ DOM バッジで判断する。
* 数値は GraphQL 応答からのみ取る。取れない行は `フォロー数`/`フォロワー数` を省いて判定する
  (数値の大小そのものは JS では判定していない)。入力が空のまま判定した件数はパネルと popup に警告として出る。
* 判定はローカル GPU の逐次処理。数百件を一気に流すと scroll のたびに待ちが出る (1 件 ~70ms、キャッシュあり)。
* 条件・閾値・bio・数値が変わるとキャッシュキーが変わるので自動で判定し直す。古い判定は TTL (既定 7 日) まで残る。
* 誤判定はゼロにできない。閾値を上げる (0.7〜0.8) と精度優先、下げると再現率優先。
